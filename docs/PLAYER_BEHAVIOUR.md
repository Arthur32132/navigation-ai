# Добыча, PvP и API управления

## Тоннели и лестничные шахты

`Miner.excavate` прокладывает проход шириной один блок. `TUNNEL` сохраняет высоту,
а `STAIRCASE_DOWN` понижает каждый следующий участок на один блок. Вход задаётся
позицией ног в уже свободной безопасной клетке. Направление только горизонтальное,
длина — 1..128 участков. Бот сначала подходит к входу, добывает верхние блоки
следующего участка, освобождает место для ног, проходит вперёд и повторяет цикл.
Для лестницы снимаются три блока высоты, чтобы сохранять просвет при спуске и возврате.

```java
ExcavationTask digging = bot.miner().excavate(
    new ExcavationRequest(bot.player().blockPosition(), Direction.NORTH,
        ExcavationMode.STAIRCASE_DOWN, 24),
    new ExcavationPolicy(96, 24000, 8, true, true)
);
int completed = digging.completedSegments();
int removed = digging.brokenBlocks();
ExcavationPhase phase = digging.phase();
```

`ExcavationPolicy` задаёт бюджет разрушений (0..4096), общий лимит времени
(1..72000 тиков), запас прочности инструмента (1..65535), сбор дропа и возврат
к входу. Нулевой бюджет позволяет пройти уже готовый проход и используется при
возобновлении задания, полностью израсходовавшего бюджет. Текущий проход и каждый
блок проверяются заново: загруженный чанк, права, дальность и видимость,
инструмент, место для дропа при `collectDrops=true` (свободный слот либо неполный
стек), твёрдый безопасный пол. Проверка запрещает
разрушение опоры под ботом, блоки с block entity, жидкости в целевой клетке и
её шести соседях, падающие блоки и неустойчивый потолок.

Добыча проходит через `ServerPlayerGameMode`: инструмент изнашивается, применяются
ванильные зачарования, возникают обычные предметы и опыт. Навигация подаёт ввод
движения; телепортация для прохода не используется. При ошибке контроллер пробует
вернуться к входу, если это разрешено и вход безопасен. Небезопасный вход и смена
измерения сразу завершают задачу. Итог сообщает причину,
частичный прогресс и подтверждение возврата. При отмене уже добытые блоки и предметы
сохраняются; обратного создания руды нет. Таймаут немедленно прекращает работу.

Чтобы продолжать шахту после боя и штатного перезапуска, включите её в последовательность:

```java
ActivityTask job = bot.activities().run(
    new BotActivity.Wait(20),
    new BotActivity.Excavate(
        new ExcavationRequest(entrance, Direction.EAST, ExcavationMode.TUNNEL, 32),
        ExcavationPolicy.defaults()),
    new BotActivity.Gather(new GatherRequest(Blocks.IRON_ORE, Items.RAW_IRON, 16),
        GatherPolicy.defaults(), NavigationPolicy.safeDefaults()),
    new BotActivity.Navigate(new NavigationGoal.ReturnGoal(home, 0.75),
        NavigationPolicy.safeDefaults())
);
```

Последовательность сохраняет завершённые участки, фактически разрушенные блоки и
израсходованное время. При продолжении передаёт остаток бюджета; прерывание не
создаёт новый полный лимит. Отдельная задача `excavate` автоматически не восстанавливается.
`Wait` также сохраняет прошедшие тики; время боевого прерывания не расходует ожидание.

Сборщик после успешной добычи приоритетно проверяет шесть соседних блоков жилы
в пределах исходной области поиска. Он выбирает безопасный подход к вновь
доступным блокам и сохраняет общий инкрементальный бюджет сканирования. Шахта
прокладывает заданную геометрию; поиск залежей в непосещённых чанках и автоматическое
ветвление шахты пока не выполняются.

## Тактика боя

В `AUTO` бот выбирает лук на дальней дистанции и ближнее оружие при сближении.
Разные пороги входа и выхода из стрельбы и задержка смены оружия предотвращают
постоянное переключение на границе дистанции. Если противник закрывается щитом,
разрешённый топор становится приоритетным на ближней дистанции. Строгие
`swordOnly()` / `bowOnly()` сохраняют ограничение семейства оружия.

```java
CombatTactics tactics = new CombatTactics(
    9.0, 5.0, 12, 1200, 80, 6.0f, true, true, true
);
CombatTask fight = bot.combat().fight(opponent,
    CombatPolicy.expert().withTactics(tactics));
CombatDiagnostics observation = fight.diagnostics();
```

Поля тактики: дистанция перехода к луку, дистанция выхода из стрельбы, задержка
смены оружия, лимит длительности, лимит отсутствия видимости, нижняя граница
здоровья, проверка безопасности движения, использование щита и топора против щита.
Здоровье задаётся в health points (два пункта — одно сердце). Стандартная тактика
останавливает бой при здоровье 4 или ниже, после 2400 тиков либо 100 тиков без
видимости. Причины — `health_limit`, `combat_timeout`, `target_not_visible`.

Перед ударом учитываются ванильная дальность взаимодействия и первая сущность
или блок на луче реального взгляда. Стрельба проверяет линию до цели, использует
упреждение, натяжение лука, расход стрел и ванильную физику снаряда. Лук отменяет
натяжение при смене оружия. Щит в offhand поднимается между ударами с учётом cooldown
и снимается перед собственной атакой. Безопасное движение проверяет коллизии,
опору под телом, жидкости, опасности и загруженность чанков при сближении,
приседании, боковом движении и отходе. Если ввод опасен, проверяется доступное
боковое движение; иначе бот останавливается.

`CombatDiagnostics` доступен у контроллера и задачи: фаза, цель, оружие, время,
потеря видимости, смены оружия, удары, выстрелы, остановки опасного движения,
дистанция, щит и причина завершения. Завершённая задача сохраняет собственный
снимок даже после запуска нового боя из callback. Пользовательская тактика
прерывания последовательности сохраняется в NBT.

## API инвентаря, наблюдения и потоков

```java
InventorySnapshot inventory = bot.inventory().snapshot();
int coal = inventory.count(Items.COAL);
int capacity = inventory.freeSlots();
bot.inventory().select(12); // перенести слот main inventory в выбранный hotbar slot
bot.inventory().equip(15, EquipmentSlot.HEAD);
BotSnapshot observation = bot.snapshot();
```

Инвентарные операции проверяют слот 0..35, подходящий тип экипировки, ограничения
сущности и запрет снятия зачарованной брони. Предметы меняются местами с прежней
экипировкой; не создаются и не выбрасываются. Изменение инвентаря отменяет текущее
корневое задание. Отказ возвращает `false`, некорректный индекс вызывает исключение.
`InventorySnapshot.slots()` каждый раз выдаёт копии стеков: изменение снимка не
меняет игрока или ранее сохранённое наблюдение. Счётчик охватывает 36 основных
слотов; броня и offhand доступны через обычный Minecraft API.

`BotSnapshot` содержит идентификатор, состояние, измерение, позицию, поворот,
здоровье, голод, статусы контроллеров и снимок инвентаря. Снимать наблюдения нужно
на серверном потоке; передавать готовые снимки другим потокам безопасно.

`bot.stopAll()` отменяет последовательность и дочерние задачи, останавливает ввод
и использование предмета. Если callback отмены успел запустить более новое
задание, метод возвращает `false` и сохраняет его управление. `BotActions.stop()`
остаётся остановкой ввода; активное задание может снова подать ввод на следующем тике.

Для обращения из внешнего потока используйте уже полученный сервис:

```java
CompletableFuture<BotSnapshot> observation = bots.submit(api ->
    api.find(botId).orElseThrow().snapshot()
);
```

`submit` всегда ставит работу в серверную очередь, возвращает результат или
исключение. Отмена future до исполнения пропускает операцию; уже начатую работу
она не прерывает. Это future операции диспетчеризации, поэтому её контракт
отличается от защитной копии `Task.completion()`. Инициализировать runtime можно
только на серверном потоке. После закрытия runtime новые задания и создание
ботов запрещены, а ожидающие операции завершаются исключением.

Новая команда, назначенная в первые тики после загрузки, имеет приоритет над
сохранённой целью. Старый журнал установленных опор остаётся доступен для
безопасного отката, даже когда сохранённый маршрут уже не возобновляется.
