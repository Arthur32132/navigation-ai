# Архитектура

Navigation AI разделён на публичный API, чистый модуль поиска и серверный runtime. Клиентская часть отсутствует.

```mermaid
flowchart LR
    L[Fabric lifecycle] --> R[BotRuntime]
    R --> H[BotHandle / ServerPlayer]
    R --> T[Server tick]
    T --> N[NavigatorImpl]
    T --> C[CombatControllerImpl]
    N --> S[WorldSnapshot]
    S --> E[Priority path scheduler]
    E --> A[GridPathfinder A*]
    A --> X[server.execute]
    X --> N
    N --> I[BotActions input]
    I --> P[ServerPlayer.doTick physics]
    R --> D[navigation_ai_bots.dat]
```

## Пакеты

| Пакет | Ответственность |
| --- | --- |
| `dev.navigationai.api` | Стабильные интерфейсы и immutable records для модов-потребителей |
| `dev.navigationai.navigation` | `GridWorld`, `GridPath`, `GridPathfinder` и детерминированный A* без Minecraft-зависимостей |
| `dev.navigationai.runtime` | Жизненный цикл fake-player, снимки мира, тик, навигация и NBT |

## Жизненный цикл fake-player

1. `BotRuntime.create` проверяет server thread и уникальность UUID.
2. Создаётся `ServerPlayer` с `GameProfile`, позицией, поворотом и стандартным `ClientInformation`.
3. К игроку прикрепляется отключённый `ServerGamePacketListenerImpl`; его `send` ничего не отправляет.
4. Игрок регистрируется через vanilla `PlayerList.placeNewPlayer`, поэтому используются обычные списки, broadcast и tracking-путь сервера.
5. На каждом серверном тике сначала обновляется навигатор, затем вызывается `ServerPlayer.doTick()`.
6. `remove` использует vanilla `PlayerList.remove`, который синхронно выполняет сохранение/очистку игрока, broadcast удаления и удаление сущности из уровня.

У fake-player нет сетевого соединения в `ServerConnectionListener`. Поэтому серверная физика запускается явно из runtime, а код, который ожидает реальный входящий packet stream, к боту неприменим.

## Боевой цикл

`CombatControllerImpl` работает в server thread перед `ServerPlayer.doTick()`. При
активном бою он временно получает приоритет над навигатором и каждый тик:

1. проверяет, что цель жива, разрешена политикой, находится в том же измерении и
   не ушла за `maxFollowDistance`;
2. выбирает меч, топор или лук из инвентаря;
3. вычисляет точку на хитбоксе, плавно ограничивает изменение yaw/pitch и подаёт
   движение относительно текущего взгляда;
4. проверяет блокирующий луч и ошибку прицеливания;
5. выполняет `ServerPlayer.attack` или реальный цикл `BowItem` только после
   задержки реакции и восстановления cooldown.

Контроллер не вызывает `hurtServer` напрямую и не корректирует траекторию после
выпуска стрелы. Это сохраняет урон, броню, зачарования, расход стрел и физику
ванильных предметов.

## Потоки и границы данных

| Операция | Поток |
| --- | --- |
| Создание/удаление игрока, NBT, чтение мира | server thread |
| `WorldSnapshot.capture`, все мутации и `Task.cancel()` | server thread |
| A* и восстановление пути | worker-поток priority scheduler |
| Применение результата и управление игроком | server thread через `server.execute` |

`WorldSnapshot` содержит только immutable-набор доступных `GridPos` и границы снимка. Worker-поток не читает `ServerLevel`, блоки, чанки или сущности напрямую. `snapshotRadius` ограничен диапазоном 4..64, а `WorldSnapshot` дополнительно уменьшает радиус до 16 при разрешённой генерации чанков. Снимки ограничены адаптивным бюджетом захватов за серверный тик; если бюджет исчерпан, запрос переносится на следующий тик.

## Навигационный цикл

1. `NavigatorImpl.goTo` отменяет предыдущую задачу и фиксирует новую цель/политику.
2. Runtime ставит tickets на локальную область при разрешённой генерации, снимает область вокруг старта, ограниченную `snapshotRadius`, и передаёт A* настоящую дальнюю цель. Неизвестная часть мира остаётся за границами снимка и не считается проходимой; генерация разрешается отдельным тик-бюджетом.
3. `GridPathfinder` ищет путь детерминированным A* с обычными шагами, спринтерскими прыжками на 2–4 блока в любом горизонтальном направлении, контролируемыми спусками до `maxFallDistance`, вертикальными и диагональными переходами, проверкой диагональных углов, опасных клеток, водного лимита и `maxPathLength`. Прыжок может пересечь яму шириной до трёх блоков или стену высотой в один блок; для диагонали дополнительно проверяется ширина тела у углов. Поиск ограничен `maxSearchNodes`; при границе снимка или исчерпании бюджета он возвращает лучший frontier-маршрут вместо пустого результата.
4. Runtime исполняет frontier-маршрут, затем снимает следующий участок от фактической позиции. Результат с номером поколения возвращается в server thread. Старый результат отбрасывается, если за это время была отмена или новое перепланирование.
5. Навигатор превращает следующий узел в yaw и стандартный ввод движения. Прыжок включается для перехода через запланированный разрыв или когда следующий узел выше текущего; контролируемый спуск выполняется обычным движением в рассчитанную посадочную клетку; в клетках с недостаточной высотой удерживается sneak, а на лестнице используется вертикальный ввод. После последнего узла финального сегмента для `PositionGoal` и `BlockGoal` может выполняться короткий прямой подход к точке/центру блока. Составные цели переходят к следующему waypoint, `LookAtGoal` сразу применяет поворот, а `DimensionGoal` выполняет серверный переход измерения.
6. При отсутствии прогресса более 40 тиков или после обнаружения новой опасности/препятствия запускается ограниченное перепланирование. После трёх безуспешных попыток задача получает `STUCK` и останавливает ввод.

Перед переходом навигатор открывает закрытую вручную открываемую дверь или люк только после проверки `mayInteract`, проверяет динамическую занятость клетки и замечает новые блоки/опасности. При изменении мира он ограниченно перепланирует маршрут. Если следующий узел содержит разрешённое препятствие, навигатор временно передаёт управление общему исполнителю `Miner`. Для перехода без опоры при `allowPlacing=true` он выбирает простой полный блок из инвентаря, проверяет разрешения и устанавливает его под переходом. После изменения мира маршрут снимается заново.

Снимок добавляет к базовой стоимости перехода оценку действий: ожидаемое время разрушения с лучшим доступным инструментом (включая Efficiency и состояние прочности) или штраф за установку опоры. Поэтому разрушение и строительство остаются допустимыми fallback-действиями, но плоский обход обычно выбирается раньше тоннеля или моста. Каждое успешное размещение попадает в журнал навигационной транзакции; при обычной отмене, ошибке или `STUCK` журнал восстанавливает исходные блоки и предметы. При штатной остановке runtime останавливает контроллеры и поиски, сохраняет итоговое состояние игрока/мира вместе с активной целью, а затем удаляет fake-player; после перезапуска навигация продолжает работу по свежему снимку.

Снимок рассматривает проходными в основном воздушные двухблочные объёмы с опорой под ногами; исходящая и текущая вода допускаются при `allowWater=true`, получают повышенную стоимость и ограничение в восемь клеток, а лава — нет. Для дальнего прыжка снимок проверяет всю траекторию: пустота, опасные клетки, диагональные углы и высота препятствия. Разрешены только стены не выше одного блока; закрытые двери, заборы и двухблочные стены не считаются прыжковыми переходами. Низкие частичные поверхности, короткие прыжки и клетки, где требуется sneak, имеют отдельные правила; закрытые низкие люки в таком туннеле не открываются автоматически. Огонь, магма, кактус, порошковый снег, лава в клетке или под опорой и соседние живые сущности попадают в immutable-набор опасностей. Это сознательно небольшой базовый слой, а не полная модель всех блоков Minecraft.

## Планирование ресурсов

Для runtime создаётся общий priority thread pool размером от 1 до 4 (`availableProcessors() - 1`, ограничение сверху 4) с bounded очередью из 64 запросов. Прямые цели получают приоритет над перестроениями `FollowGoal`, а одинаковые приоритеты выполняются FIFO. При отмене старый `Future` прерывается, а A* периодически проверяет interrupt-флаг. Бот не получает отдельный поток. Серверный тик не ждёт завершения A*: он продолжает симуляцию, пока задача находится в `COMPUTING`.

Параметры, которые ограничивают работу одного поиска:

- `snapshotRadius` ограничивает объём чтения мира и валидируется в диапазоне 4..64;
- `maxSearchNodes` ограничивает число раскрытых узлов и валидируется в диапазоне 128..200000;
- `maxPathLength` валидируется в диапазоне 1..16384;
- priority scheduler ограничивает параллелизм и размер очереди поиска;
- бюджет снимков ограничивает синхронное чтение мира на одном серверном тике.

При росте числа ботов runtime автоматически снижает лимиты снимков, A* и генерации чанков; при медленном тике лимиты дополнительно уменьшаются. Это делает десятки ботов предсказуемее, но не является гарантией конкретного TPS: стоимость `ServerPlayer.doTick`, сущностей и чанков остаётся на сервере.

## Сохранение

На `SERVER_STOPPING` runtime сначала останавливает контроллеры, отменяет только поисковые worker-задачи и сохраняет список ботов в сжатый NBT-файл `<world>/navigation_ai_bots.dat`. Запись строится во временный файл и заменяет основной через atomic move с безопасным fallback, поэтому ошибка записи не обнуляет последнюю рабочую копию. Для каждого бота сохраняются имя, измерение и данные `ServerPlayer` через `saveWithoutId`. Если навигатор выполняет задачу, рядом сохраняются тип цели (включая составные цели и измерение), её координаты или UUID цели игрока, а также все поля `NavigationPolicy`.

При загрузке сначала восстанавливаются fake-player и их предметы/позиции, затем активные цели перечитываются из NBT и запускаются заново по свежему снимку мира. Это намеренно не продолжение старого пути: маршрут строится заново, поэтому изменения чанков между остановкой и запуском учитываются. Цель `FollowGoal` разрешается по UUID после создания всех сохранённых ботов; недоступная или повреждённая цель пропускается с предупреждением. Если измерение недоступно, конкретный бот пропускается, а файл сохраняется для ручного восстановления.
