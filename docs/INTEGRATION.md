# Интеграция в другой серверный мод

Для жителей используйте `BotService.createVillager(...)` или `attach(Villager)`.
Общий код получает тело через `BotHandle.entity()` и работает с предметами через
`BotInventory`; `player()` сохраняется для ботов-игроков. Полный пример и правила
сохранения: [управление жителями](VILLAGERS.md).

Готовый самостоятельный потребитель — [Autonomous Bots](../../AutonomousBots/README.md).
Его планировщик использует `BotService.create`, `collector().gather`,
`miner().excavate`, `navigator().goTo`, `combat().fight` и `BotInventory`.
Приоритеты жизни, ванильный крафт, обслуживание собственных печей и грядки
реализованы в отдельном моде. Дополнительные данные UUID/лагеря сохраняются
модом-потребителем, а физическое состояние и инвентарь — библиотекой.
Переход к еде или спасению прерывает текущую работу через `stopAll()`;
после завершения прерывания планировщик выбирает новую работу по текущим
предметам, не переиспользуя отменённый `Task`.

Снимок маршрута и проверка движения учитывают колючие ягодные кусты
(`SweetBerryBushBlock.AGE > 0`) как опасность. Только что посаженный куст
с возрастом 0 безопасен. Потребитель, спасая NPC из уже занятой опасной клетки,
должен проверять всё тело игрока и удерживать управление до выхода:
безопасный блок под координатой ног ещё не означает, что NPC освободился.

## Подключение JAR

Для локальной разработки положите `navigation-ai-0.1.0.jar` в каталог `libs` своего мода и добавьте его в Gradle classpath. Для Fabric Loom обычно достаточно:

```groovy
dependencies {
    modCompileOnly files("libs/navigation-ai-0.1.0.jar")
    modRuntimeOnly files("libs/navigation-ai-0.1.0.jar")
}
```

В `fabric.mod.json` мода-потребителя добавьте зависимость, чтобы Fabric загрузил библиотеку раньше вашего entrypoint:

```json
"depends": {
  "navigation_ai": ">=0.1.0"
}
```

На сервере библиотека должна находиться в `mods` вместе с Fabric API. Fabric Loader проверит Minecraft 26.2, Java 25+ и наличие Fabric API по `fabric.mod.json`.

## Инициализация

Получайте сервис после запуска сервера. Все изменяющие состояние обращения к API — создание/удаление, прямые действия, запуск и отмена задач — выполняются в server thread:

```java
public final class GuardMod implements ModInitializer {
    @Override
    public void onInitialize() {
        ServerLifecycleEvents.SERVER_STARTED.register(server -> {
            BotService bots = NavigationAiMod.runtime(server).service();
            BotHandle guard = bots.create(BotCreateOptions.at(
                "Guard",
                server.overworld(),
                new Vec3(0.5, 80, 0.5)
            ));

            guard.navigator().goTo(
                new NavigationGoal.PositionGoal(new Vec3(100.5, 80, 100.5)),
                NavigationPolicy.safeDefaults()
            );
        });
    }
}
```

В реальном моде удобно хранить `BotHandle` по UUID или по собственной роли. `BotService.find(...)` возвращает `Optional`, а `bots()` возвращает снимок коллекции, который можно безопасно перебирать в текущем тике.

## Вызовы из внешнего потока

Сохраните сервис, полученный в `SERVER_STARTED`, и отправляйте операции через
`BotService.submit`. Операция исполняется на серверном потоке; результат может
быть прочитан из другого потока:

```java
CompletableFuture<BotSnapshot> observation = bots.submit(api ->
    api.find(guardId).orElseThrow().snapshot()
);

CompletableFuture<NavigationTask> started = bots.submit(api ->
    api.find(guardId).orElseThrow().navigator().goTo(goal, policy)
);
CompletableFuture<NavigationResult> arrived = started.thenCompose(NavigationTask::completion);
```

Первая future завершится после снятия наблюдения. `started` завершится после
назначения цели; `arrived` — после завершения навигации. Если операция бросает
исключение, `submit` передаёт его в future. Отмена этой future до исполнения
пропускает операцию, но не прерывает уже начатый код. Инициализация runtime
из внешнего потока запрещена; сервис получают заранее на серверном потоке.

## Инвентарь и наблюдение

На серверном потоке используйте копии содержимого и проверяемые операции:

```java
InventorySnapshot inventory = guard.inventory().snapshot();
int arrows = inventory.count(Items.ARROW);
int emptySlots = inventory.freeSlots();
boolean equipped = guard.inventory().equip(12, EquipmentSlot.HEAD);
BotSnapshot state = guard.snapshot();
```

В примере `equip` предполагает подходящий шлем в основном слоте 12. Предмет
меняется местами с прежней экипировкой. `select(0..8)` выбирает hotbar slot,
а `select(9..35)` переносит основной слот в текущий hotbar slot обменом стеков.
Эти мутации отменяют текущее корневое задание. Отказ экипировать предмет или
новое задание из callback отмены возвращают `false`; некорректный индекс
вызывает исключение до изменения содержимого.

`count` и `freeSlots` относятся к 36 основным слотам; `freeSlots` считает пустые
слоты, а не суммарную вместимость частично заполненных стеков. Готовые снимки
можно передавать в UI или worker-поток. `InventorySnapshot.slots()` выдаёт
копии стеков, поэтому изменение снимка не меняет игрока. Ссылки из `player()`
и контроллеров продолжают подчиняться обычным правилам серверного потока.

## Обработка результата

`completion()` каждой задачи возвращает защитную копию `CompletableFuture`. Для отмены
самой задачи вызывайте её `cancel()` на серверном потоке; отмена ожидания или
`arrived` из примера выше не останавливает бота. Это относится к навигации,
добыче, шахте, сбору, бою и последовательности действий. Не изменяйте мир
непосредственно из неизвестного callback-потока: передайте продолжение в
`bots.submit(...)` или `server.execute(...)`.

```java
NavigationTask task = guard.navigator().goTo(goal, policy);
task.completion().whenComplete((result, error) -> server.execute(() -> {
    if (error != null || result.status() != NavigationStatus.SUCCESS) {
        // Зафиксировать причину завершения.
        return;
    }
    // Следующая серверная команда после прибытия.
}));
```

## Полная остановка и ручной ввод

```java
if (guard.stopAll()) {
    guard.actions().look(90, 0);
    guard.actions().setMovement(0, 1, false, false, false);
}

// Та же остановка из внешнего потока:
CompletableFuture<Boolean> stopped = bots.submit(api ->
    api.find(guardId).orElseThrow().stopAll()
);
```

`stopAll()` отменяет корневое задание и дочерние операции, сбрасывает ввод и
использование предмета. Если callback отмены начал новое задание, метод
возвращает `false`, сохраняя его управление; ручной ввод в примере тогда не
подаётся. `BotActions.stop()` сбрасывает только ввод: активный контроллер может
снова назначить движение на следующем тике.

## Следование

```java
NavigationTask follow = guard.navigator().follow(
    new NavigationGoal.FollowGoal(targetPlayer, 3.0, 4.0),
    NavigationPolicy.safeDefaults()
);
```

`repathDistance` определяет, насколько далеко должен переместиться target, чтобы запустить новый поиск. Следование между измерениями не поддерживается текущим runtime.

Навигация открывает вручную открываемые двери и люки, включая медные варианты с ручным открытием, и проверяет `ServerPlayer.mayInteract(...)`. Разрушение препятствий и установка опор также подчиняются этому разрешению; в защищённой области боту нужны соответствующие права. Вода (включая текущую) разрешается политикой `allowWater` и получает повышенную стоимость, поэтому сухой путь предпочтительнее, но длинный водный маршрут допустим; лава не используется как проходная клетка. Спринтерские прыжки через ямы до трёх блоков, включая диагональные, и через стену высотой в один блок выполняются автоматически; опасные клетки, заборы, закрытые двери и более высокие препятствия не считаются безопасным прыжком. В низких проходах бот удерживает sneak.

## Несколько десятков ботов

Создавайте ботов пакетно в server thread, например во время `SERVER_STARTED` или через `server.execute`. Не создавайте их из собственного worker-потока.

```java
for (int i = 0; i < 50; i++) {
    BotHandle bot = bots.create(BotCreateOptions.at(
        "worker_" + i,
        server.overworld(),
        new Vec3(0.5 + i, 80, 0.5)
    ));
    bot.navigator().goTo(target, NavigationPolicy.safeDefaults());
}
```

Планировщик использует общий priority scheduler максимум с четырьмя worker-потоками и очередью на 64 запроса. Прямые цели получают приоритет над перестроениями `FollowGoal`, отменённые запросы удаляются из очереди. Снимок мира собирается на серверном потоке порциями: максимум 4096 позиций за тик для всех ботов и 2048 за вызов одного бота; одновременно стартует не более четырёх новых снимков за тик. Первичный горизонтальный радиус снимка не превышает 16 блоков и для близкой цели уменьшается до расстояния до неё плюс четыре блока, но не ниже восьми при достаточно большой политике. Если путь к близкой цели не найден, радиус расширяется до `snapshotRadius`; по вертикали снимок может охватывать до 32 блоков в сторону цели. `snapshotRadius` принимается только в диапазоне 4..64 как верхний предел, `maxSearchNodes` — 128..200000, `maxPathLength` — 1..16384. Для 10–50 ботов следует проверять нагрузку на реальной сцене.

Для проверки нагрузки интегратор может читать `NavigationAiMod.runtime(server).metrics()` и
логировать `averageTickMillis()`, `averagePathSearchMillis()`, `queuedSearches()` и
`replans()`. Снимок безопасно сохранять или передавать в собственную систему мониторинга.

## Удаление

```java
guard.remove();
```

`remove()` сам отменяет задания и освобождает ресурсы бота. При остановке
сервера runtime запрещает новые задания, завершает ожидающие `submit`
исключением, останавливает контроллеры и сохраняет активные намерения вместе
с журналом уже размещённых блоков атомарно в NBT. Затем fake-player удаляется
через vanilla `PlayerList.remove`.

Обычная отмена/ошибка откатывает журнал; после перезапуска он восстанавливается
до построения нового пути. Откат меняет только клетки, где сохранилось состояние
блока, установленное ботом. Активные навигационные цели всех типов и их
`NavigationPolicy` назначаются снова по свежему снимку мира. Команда, назначенная
интегратором в первые тики после загрузки, имеет приоритет над сохранённым
намерением, сохраняя возможность безопасного отката прежних опор.

Отдельные задачи добычи, шахты, сбора и боя автоматически не возобновляются;
для продолжения используйте сохраняемые [последовательности действий](ACTIVITIES.md).
Они восстанавливают прогресс и остаток бюджета `Excavate`, прошедшие тики `Wait`
и пользовательскую `CombatTactics` прерывания. Недоступная цель игрока для
follow/escort пропускается.

После перезапуска получите новый сервис и найдите восстановленного бота по UUID.
Старые `BotHandle`, задачи и их future относятся к предыдущему runtime и не
переходят в новое выполнение.

Сборщик ресурсов обрабатывает неудачный подход (`FAILED`, `CANCELLED` или `STUCK`) как повод выбрать другую позицию из продолжающегося скана, поэтому интегратору обычно достаточно наблюдать за `GatherTask` и его итоговым `GatherStatus`.
