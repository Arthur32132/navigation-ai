# Управление жителями

Navigation AI поддерживает два тела: серверного игрока и настоящего ванильного
жителя. Оба используют общий API навигации, добычи, сбора, тоннелей/лестничных шахт,
боя, инвентаря и последовательностей заданий.

```java
BotService bots = NavigationAiMod.runtime(server).service();

// Новый житель или уже существующий загруженный житель:
BotHandle worker = bots.createVillager(BotCreateOptions.at("Miner", level, position));
BotHandle resident = bots.attach(existingVillager);

worker.inventory().insert(new ItemStack(Items.IRON_PICKAXE));
worker.activities().run(List.of(
    new BotActivity.Navigate(new NavigationGoal.PositionGoal(entrance), NavigationPolicy.safeDefaults()),
    new BotActivity.Excavate(request, ExcavationPolicy.defaults()),
    new BotActivity.Navigate(new NavigationGoal.ReturnGoal(home), NavigationPolicy.safeDefaults())
));

LivingEntity actualBody = worker.entity();
BotKind kind = worker.kind(); // VILLAGER

// Сопровождать можно и другого жителя:
resident.navigator().follow(new NavigationGoal.EntityFollowGoal(worker.entity(), 2), NavigationPolicy.safeDefaults());
```

Все операции изменения состояния выполняются в серверном потоке, как и у игроков.
`BotService.submit(...)` работает с обоими видами. `attach` повторно возвращает тот же
handle для уже подключённого жителя.

## Сущность и действия

`entity()` возвращает настоящую сущность мира. `player()` и `actions().player()`
сохраняют прежнее поведение для ботов-игроков; у жителей они явно выбрасывают
`UnsupportedOperationException`. Для общего кода используйте `entity()`,
`inventory()`, `snapshot()` и контроллеры, а не приведение к `ServerPlayer`.

Житель не добавляется в PlayerList, не получает сетевое соединение и не становится
вторым физическим телом. Внутренний незарегистрированный контекст нужен для
ванильных операций, которые требуют Player: разрушения блоков, расчёта инструмента
и заряженного удара. Движется, получает урон и блокирует щитом сам житель. Источник
ближнего урона и владелец стрелы — настоящий житель. Лук использует ванильные
операции расходования боеприпасов, зачарований и износа.

Встроенный Brain временно уступает управление при задании или ручном движении.
После остановки заданий обычное поведение возобновляется. Профессия, торговые
предложения и собственный пищевой инвентарь жителя сохраняются.

## Инвентарь и жизненный цикл

- Рабочий рюкзак содержит 36 слотов и выбираемый слот руки. Ванильные восемь
  пищевых слотов остаются отдельными: библиотека не создаёт и не переносит еду
  между ними автоматически.
- `inventory().insert(stack)` вставляет копию и возвращает остаток;
  `extract(slot, count)` извлекает предметы. Обе операции учитывают отмену текущего
  задания и не меняют переданный вызывающим кодом ItemStack.
- Выбор руки и экипировка отражаются на настоящем теле. Видимость брони/оружия
  ограничена ванильной моделью жителя: новый рендерер библиотека не добавляет.
- `stopAll()` отменяет работу, сохраняя подключение. `detach()` отменяет работу,
  оставляет живого жителя и экипировку, а остальные предметы рюкзака возвращает
  дропами рядом. `remove()` удаляет саму сущность вместе с handle.
- Рюкзак, активная навигация, журнал опор и последовательности сохраняются в
  `navigation_ai` внутри NBT жителя. Его собственная сущность сохраняется обычным
  механизмом чанков. В `navigation_ai_bots.dat` жители не дублируются.
- При настоящей выгрузке старый handle перестаёт действовать; после загрузки
  используйте `bots.find(uuid)`. Маршруты пересчитываются по текущему миру.
- Пока житель выполняет работу, отдельные учитываемые по ссылкам tickets удерживают
  загрузку и симуляцию его текущей области. При стрельбе область расширяется до
  дальности лука (радиус ticket ограничен 6), чтобы стрелы и цели продолжали
  двигаться за границей чанка. После работы tickets освобождаются с запасом
  40 тиков для чтения результата. Игровые player tickets не меняются.

## Возможности тела

Поиск проверяет фактические размеры жителя, включая возраст. Управляемый житель
использует физический спринт и прыжок LivingEntity; скорость учитывает атрибуты.
Sneak тормозит у края, но не уменьшает ванильный рост жителя: для низкого прохода
нужен обход либо разрешённое разрушение. `DimensionGoal` сохраняет handle при
переходе: Minecraft может создать новую сущность в другом измерении, и библиотека
переподключает исполнителя к ней.

У жителей нет игроковой шкалы голода; `snapshot().foodLevel()` возвращает `-1`.
Эта поддержка расширяет инструменты библиотеки. Самостоятельный планировщик
`Autonomous Bots`, который обращается непосредственно к Player для голода,
крафта и сна, требует отдельной адаптации при использовании с жителями.

## Проверка

`tools/regression/VillagerRegression.java` добавляет команду `navvillagers` в тестовый
мод. Выполнять только в отдельном мире: сценарии изменяют площадку около
X=11000, Z=11000, Y=200, создают сущности и проверяют реальные действия сервера.
`navvillagers-save` и `navvillagers-restore` проверяют сохранение через настоящий
перезапуск. Тестовые команды отсутствуют в JAR библиотеки.
