# Navigation AI

Серверная библиотека для Fabric/Minecraft 26.2. Она создаёт fake-player на стороне сервера, сохраняет его состояние и предоставляет API для физического управления и навигации. Клиентский мод для работы библиотеки не нужен.

Текущий артефакт — `navigation-ai:0.1.0`. Публичный API сохраняет совместимость с текущими модами-потребителями, а базовый исполнитель навигации поддерживает сегментированные дальние маршруты и разрешённые действия с блоками.

## Быстрый старт

Требования:

- Minecraft Java 26.2;
- Fabric Loader 0.19.5 или новее;
- Fabric API `0.161.0+26.2` или совместимая сборка для 26.2;
- JDK 25 или новее.

Собрать библиотеку:

```text
gradlew.bat clean build
```

Готовый файл находится в `build/libs/navigation-ai-0.1.0.jar`. Положите его в `mods` серверного экземпляра вместе с Fabric API. Для мод-потребителя добавьте этот JAR в compile/runtime classpath. Все изменяющие состояние вызовы, включая `BotActions`, `goTo`, `cancel` и `Task.cancel()`, выполняйте в server thread или передавайте через `server.execute(...)`.

Минимальный пример:

```java
BotService bots = NavigationAiMod.runtime(server).service();
BotHandle guard = bots.create(BotCreateOptions.at(
    "Guard",
    server.overworld(),
    new Vec3(0.5, 80, 0.5)
));

NavigationTask task = guard.navigator().goTo(
    new NavigationGoal.PositionGoal(new Vec3(100.5, 80, 100.5)),
    NavigationPolicy.safeDefaults()
);
```

Подробные примеры и правила потоков находятся в [руководстве по интеграции](docs/INTEGRATION.md). Описание всех интерфейсов — в [API](docs/API.md), устройство runtime — в [архитектуре](docs/ARCHITECTURE.md).

## Что работает сейчас

- fake-player регистрируется в `ServerLevel` и `PlayerList`, виден серверным системам как `ServerPlayer`;
- серверная физика вызывается каждый тик через `ServerPlayer.doTick()`;
- доступны движение, прыжок, спринт, sneak и поворот;
- доступны разрушение одного блока и сбор заданного количества предметов через `Miner`/`ResourceCollector`;
- доступен бой с мобами и игроками через `CombatController`: лучший доступный меч, лук и запасной топор;
- `CombatPolicy.swordOnly()` и `CombatPolicy.bowOnly()` позволяют стороннему моду строго выбрать оружие;
- есть профили `STANDARD` и `EXPERT` с задержкой реакции, ограниченной скоростью поворота и разной точностью прицеливания;
- навигация использует ограниченный детерминированный A* по неизменяемому снимку мира с проверкой диагональных коллизий, опасных клеток и длины пути; учитывает частичные и waterlogged collision shape, fence gate, двери, вручную открываемые люки (включая медные), плиты, ступени, спринтерские прыжки через ямы шириной до трёх блоков по прямой и диагонали, а также через стену высотой в один блок, контролируемый спуск с уступов, узкие проходы с приседанием, подъём по лестницам и перепланирование маршрута при динамических препятствиях;
- снимок различает исходящую и текущую воду, а также лаву; вода допускается при `allowWater=true` без отдельного ограничения длины, но получает повышенную стоимость, поэтому сухой обход предпочтительнее. Лава всегда исключается из проходимых клеток. Огонь, магма, кактус, порошковый снег и лава под ногами учитываются как опасности; клетки, занятые живыми существами, исключаются из маршрута;
- снимок начинается с локального радиуса до 16 блоков по горизонтали и расширяется до предела `snapshotRadius`, если вход к близкой цели лежит за его границей; по вертикали снимок охватывает минимум 16 блоков и до 32 блоков в сторону цели. Дальние цели выполняются последовательными сегментами, а поиск у ещё загружаемых чанков ограниченно повторяется. При смещении бота течением во время построения снимка навигатор продолжает поиск от новой позиции в уже считанной области;
- на последнем локальном сегменте навигатор продолжает короткий подход с живой проверкой коллизий, опоры, опасностей и sneak, пока не выполнится заданный `tolerance` без дополнительного запаса. `BlockGoal` ищет все доступные соседние клетки, а допуск измеряется от позиции бота до центра блока; если подход невозможен, задача завершается `STUCK` после ограниченного числа перепланирований;
- есть цели `BlockGoal`, `PositionGoal`, `FollowGoal`, `LookAtGoal`, `ReturnGoal`, `PatrolGoal`, `EscortGoal`, `MultiGoal` и `DimensionGoal`;
- `tolerance` и дистанция follow участвуют в условии прибытия, а застревание завершается статусом `STUCK` после ограниченного числа перепланирований;
- по явной политике навигатор может разрушать препятствия и устанавливать простые полные блоки для опор;
- дальние цели планируются по настоящей дальней цели: при границе снимка A* возвращает лучший frontier-сегмент, после его исполнения маршрут продолжается с нового снимка; при явном `allowChunkGeneration` runtime удерживает navigation tickets и ограничивает генерацию отдельным бюджетом;
- поиск выполняется в общем priority scheduler максимум с четырьмя worker-потоками и очередью из 64 запросов; прямые цели получают приоритет над follow-перестроениями, а бюджеты снимков и узлов адаптируются к числу ботов и длительности тика;
- runtime предоставляет read-only `NavigationMetrics` с tick cost, временем снимков/A*, узлами, очередью, отменами, перепланированиями и причинами автоматической разгрузки;
- при `STUCK` во время перемещения к ресурсу `ResourceCollector` возвращается к поиску и пробует следующий допустимый подход, не оставляя сборщик в зависшем состоянии;
- `FollowGoal` сохраняет текущий маршрут во время фонового поиска; новый маршрут применяется только из безопасной позиции на нём;
- захват снимков и поиск ресурсов имеют общий бюджет времени 2–5 мс на тик; боты получают работу по очереди со сменой первого бота, а бюджет реагирует на среднюю длительность полного серверного тика;
- сбор ресурсов проверяет не более 512 клеток на бота и 1024 на runtime за тик, резервирует выбранный блок до завершения попытки и распределяет сортировку кандидатов по времени сканирования;
- планирование опор учитывает число безопасных полных блоков в инвентаре; магма, падающие блоки и блоки с block entity не используются;
- состояние игрока и активные навигационные цели всех типов с их `NavigationPolicy` сохраняются атомарно в `navigation_ai_bots.dat` в корне мира и восстанавливаются после перезапуска; маршрут после загрузки строится заново по текущему миру;
- `NavigationPolicy` ограничивает ресурсоёмкие параметры: `snapshotRadius` — 4..64 (верхний предел горизонтального радиуса снимка), `maxSearchNodes` — 128..200000, `maxPathLength` — 1..16384; цели и параметры создания бота отклоняют обязательные `null`, `NaN` и бесконечные координаты/значения;

Установка и разрушение в составе маршрута требуют явного включения `allowBreaking`/`allowPlacing`. Исполнитель повторно проверяет права, инструмент, инвентарь и фактическое состояние мира, учитывает Efficiency при выборе инструмента и откатывает журнал частичных размещений при обычной отмене, ошибке или `STUCK`. При штатной остановке сервера runtime сначала останавливает worker-задачи, сохраняет активную навигацию и размещённые блоки, а затем удаляет fake-player, чтобы маршрут продолжился после перезапуска. Крафт, транспорт, элитры и сложные блоковые механизмы остаются за пределами текущего исполнителя.

Явная добыча ресурсов также доступна через `bot.miner().breakBlock(...)` и `bot.collector().gather(...)`.

После разрушения waterlogged-блока `MiningTask` сообщает успех, даже если в его клетке осталась вода. Во время навигационного разрушения ожидание добычи не считается застреванием, а завершение маршрута с ошибкой или `STUCK` отменяет ещё активную добычу. При перезапуске вместе с целью восстанавливается журнал уже размещённых опор, поэтому последующая отмена может вернуть блоки и материалы.

## Проверка

```text
gradlew.bat test
gradlew.bat clean build
```

`runServer` предназначен только для ручной smoke-проверки. Перед первым полноценным запуском тестового сервера примите EULA в `run/eula.txt`.
