# Проверка на настоящем Fabric-сервере

Поддержку жителей проверяет `VillagerRegression.java`: `navvillagers` запускает
23 сценария (включая лук за границей чанка без принудительной загрузки, опоры,
возврат из лестничной шахты, выгрузку/загрузку, маленького жителя с NoAI и добычу
под водой). Площадка — X/Z около 11000, Y=200; тесты удерживают свою площадку
загруженной между случаями, чтобы сохранённые тестовые мобы не попадали в следующий
сценарий. Последний сценарий лука снимает это удержание и проверяет только tickets
библиотеки. `navvillagers-case <0..22>` запускает один случай.

Полный отдельный прогон с настоящим перезапуском:

```text
python tools/regression/run-validation.py --server-template ../navigation-fixes-validation/server --suite villagers,villager-persistence
```

Подробности API — [жители](../../docs/VILLAGERS.md).

Проверка расширения добычи, PvP и API: [30.09.2026](../../docs/VALIDATION_2026-09-30.md).
Сводка двух прогонов и неизменённые исходные отчёты сохранены в
[results/2026-09-30](results/2026-09-30/summary.json).

Последний полный успешный прогон: [27.09.2026](../../docs/VALIDATION_2026-09-27.md).
Исходный [JSON](results/2026-09-27/report.json),
[траектория CSV](results/2026-09-27/journey.csv) и
[график](results/2026-09-27/journey.png) сохраняются вне `build`.

Java-классы этого каталога — интеграционные сценарии для Minecraft 26.2.
Они компилируются в отдельный тестовый мод `Practicetestmod`, а не в библиотеку.
Тесты выполняются на серверных тиках и проверяют результат через публичный API
и состояние мира. Клиент не требуется.

## Подключение к тестовому моду

Перед ручным подключением можно использовать готовый автоматический прогон ниже.

### Автоматический полный прогон

Из корня библиотеки:

```text
python tools/regression/run-validation.py --server-template ../navigation-fixes-validation/server --profile
```

Скрипт собирает библиотеку с JUnit и мод-потребитель, затем создаёт отдельный сервер
в `build/validation/YYYYmmdd-HHMMSS/server`. Из шаблона копируются только launcher
Fabric Loader 0.19.5, установленные бинарные файлы `.fabric/server`, `libraries`,
`versions`, Fabric API и уже принятая EULA. Шаблон должен успешно запускаться
хотя бы один раз; новые прогоны используют его готовый launcher cache.
Мир, настройки, операторы и прочие моды шаблона не копируются. Порт по умолчанию
25582, адрес 127.0.0.1. Мир обычный, seed 8675309, survival, difficulty peaceful.
Нужны Python 3 и JDK 25; JDK обнаруживается через `JAVA_HOME` или Gradle toolchain.

Порядок по умолчанию:
`library,excavation,combat,core,activities,persistence,excavation-persistence,regions,journey,mixed,load`.
`--suite library,excavation,combat` выбирает новые API, добычу и PvP;
`--suite excavation-persistence` проверяет настоящий перезапуск во время шахты.
`--suite activities,persistence` выбирает продолжение действий и сбор после
перезапуска. `--distance 1000`
задаёт длину природного маршрута, `--seed` и `--port` меняют мир/порт.
`--consumer` указывает другой checkout тестового мода. `--keep-going` продолжает
следующие независимые стадии после отрицательного результата. `--profile` сохраняет
JFR и GC log, в том числе отдельные файлы после перезапуска. `--no-build` использует
уже собранные JAR; JUnit-результаты тогда относятся к последней сборке.
`--suite transitions` отдельно запускает десять сочетаний переходов; они также
входят в `core`.

Скрипт возвращает ненулевой exit code при провале или таймауте. `report.json`
содержит итог каждой стадии, события/длительности, SHA-256 обоих JAR и исходников,
базовый Git commit и состояние рабочей копии. Логи сборки и сервера сохраняются
рядом. После прогона сервер штатно останавливается, новый мир остаётся на диске.
Для досрочной остановки создайте файл `stop-requested` в каталоге данного отчёта:
скрипт отправит серверу `stop` и сохранит отчёт о прерванном запуске.

| Команда | Проверка |
| --- | --- |

| `navexcavation` | 12 сценариев тоннеля и лестницы с физическим возвратом, жидкостей, потолка, контейнеров, инструмента, бюджета, владения контроллерами, видимости и открывшейся жилы |
| `navcombat` | 11 сценариев стрел и перехода к ближнему оружию, урона заряженного меча, строгого режима, лимитов здоровья/видимости/времени, перекрытия атаки сущностью, края площадки, щита, топора и callback |
| `navactivities` | 17 сценариев владения контроллерами, продолжения после боя, отмены, callback, NBT и безопасной добычи из пола |

| `navregions` | Длинный тупик с обходом за пределами локального снимка и возвратом по графу |
| `navreality journey 1000` | Survival-бот проходит природный рельеф; промежуточные чанки загружает/генерирует навигация |

Арены изменяют блоки и удаляют тестовых ботов; запускайте их в отдельном мире.
`navlibrary` использует область около X/Z=9000, `navexcavation` и `navcombat` —
около X/Z=12000, а проверка перезапуска шахт — около X/Z=14000. Шахтная арена
затрагивает уровни Y=192..204. Команды выполняйте последовательно: у проверок
добычи и боя общая область. NBT roundtrip в `navlibrary` выполняется внутри
одного runtime; `excavation-persistence` отдельно подтверждает сохранение
на диск, штатную остановку и загрузку новым процессом сервера.
Природный маршрут подготавливает только два чанка конечных точек. После старта
нет телепортации, полёта или бессмертия. Бот получает алмазные инструменты и
материал для опор. Проверяются результат, здоровье, фактическая траектория и
очистка tickets/резервов; измеряются полные server tick и отдельно runtime с
средним, p95, p99 и максимумом. Подготовка искусственных арен не входит в эти
интервалы. Накопительные `NavigationMetrics` охватывают всю жизнь данного runtime.
В корне тестового мира остаётся `navigation-journey.csv` с координатами и здоровьем
раз в секунду, включая старт и конец природного маршрута.

Зафиксированная исходная точка — Git tag `stable-2026-09-26`. В этой рабочей копии
предыдущие JAR также сохранены в `build/stable-2026-09-26`; сборка `clean` удаляет
этот локальный каталог, поэтому для повторной сборки старой версии используйте тег.

### Ручное подключение

В `Practicetestmod/build.gradle` добавьте:

```groovy
sourceSets.main.java.srcDir('../MinecraftmodNavigationAi/tools/regression')
```

В инициализаторе `Practicetestmod` из пакета `dev.navigationaitest` вызовите:

```java
RuntimeRegression.register();
LibraryApiRegression.register();
ExcavationRegression.register();
CombatTacticsRegression.register();
ExcavationPersistenceRegression.register();
```

В дерево команд `navtest` добавьте:

```java
.then(Commands.literal("regression").executes(context -> RuntimeRegression.start(context.getSource())))
```

Скопируйте актуальную библиотеку в `Practicetestmod/libs`, выполните `clean build`
в обоих проектах и установите оба JAR в `mods` тестового сервера.

## Запуск

Используйте **отдельный одноразовый мир**: тест перестраивает площадку
X/Z=1008..1088, Y=199..205, создаёт и удаляет тестовых ботов и предметы.
Пример аргументов запуска сервера:

```text
java -Xms1G -Xmx2G -jar fabric-server-mc.26.2-loader.0.19.5-launcher.1.1.2.jar nogui --universe C:/minecraftWorkflow/regression-universe --port 25566
```

В консоли сервера:

```text
navlibrary
navexcavation
navcombat
navtest selftest
navtest ticket-regression
navtest regression
navreview
navtransitions
```

Ожидаемые результаты: `SELFTEST PASS (22 checks)` и
`REGRESSION PASS passed=51 failed=0`, а для расширений —
`LIBRARY PASS passed=15 failed=0`, `EXCAVATION PASS passed=12 failed=0` и
`COMBAT PASS passed=11 failed=0`. Эти строки задают критерии успешного прогона;
подтверждённые результаты сохраняются в отдельном отчёте validation.
Обычные сценарии ограничены 400 тиками,
длинный водный маршрут — 800, а возврат из-под высокого финиша — 700. Для одного сценария используйте
`navtest regression-case <0..47>` для ранее доступных отдельных сценариев; новые
сценарии 48–50 пока запускаются только полным `navtest regression`;
при ошибке в журнале появляются `REGRESSION ERROR` и диагностическое состояние.
Перед регрессией в отдельном мире задайте `difficulty peaceful`, чтобы
естественно появившиеся мобы не перекрывали тестовые коридоры. Завершайте
сервер командой `stop`.

`NavigationTicketRegression.java` компилируется в пакет `dev.navigationai.runtime`
тестового мода. Команда `navtest ticket-regression` проверяет на настоящем
`TicketStorage` два пересекающихся маршрута: освобождение первого сохраняет
билеты второго, освобождение последнего удаляет только `navigation_ai:navigation`,
а исходные `PLAYER_LOADING` и `PLAYER_SIMULATION` остаются. Ожидаемый результат —
`TICKET REGRESSION PASS`. Проверка не меняет блоки и восстанавливает временные
билеты в `finally`.

`ReviewRegression.java` регистрирует команду `navreview` для 15 сценариев,
добавленных после глубокого ревью: высота над плитой, выбор доступной стороны
блока, движущаяся Follow-цель, повторный запуск добычи/сбора/боя из callback,
новая опасность на финальном подходе, опасный материал и нехватка опор,
метрики составной цели, инкрементальный скан, освобождение резервирования и
новое препятствие в середине прыжка, новый порошковый снег на маршруте и равное распределение скана между четырьмя сборщиками. Ожидается
`REVIEW PASS passed=15 failed=0`. Запускайте после завершения `navtest regression`;
площадка занимает X=1004..1054, Z=1004..1044, Y=199..205 и меняется при каждом тесте.
Команды регрессии и нагрузочные прогоны нужно выполнять последовательно.

`TransitionRegression.java` регистрирует `navtransitions`: десять сочетаний
движений и внешних условий. Проверяются дверь перед последовательными прыжками,
плита под низким потолком, устойчиво недоступный спринт, течение, толчок в полёте,
изменение посадочной клетки, препятствие впереди при движении, кеш Follow-пути
попадание в радиус Follow-цели до приземления над разрывом и спуск на один блок
под нависающим препятствием, где требуется обход.
Для каждого случая выводятся время до первого движения, перепланирования,
снижение здоровья, повторно использованные клетки и максимальная пауза.
Срок задачи — 650 тиков; незавершённые задачи учитываются как `dangling`.
Ожидается `TRANSITIONS PASS passed=10 failed=0 dangling=0`.
Площадка расположена около X/Z=3072, Y=196..206; тест также удаляет всех ботов
одноразового сервера. В peaceful тест удерживает низкую сытость явно, чтобы
автоматическое восстановление не возвращало спринт.

`navfixes` проверяет 15 случаев. В том числе снимок снимается непосредственно
после асинхронного запроса нового чанка: ticket уже существует, но FULL-чанк
ещё не готов. Снимок должен пропустить его, сохранив future незавершённым;
синхронная загрузка ради чтения блоков считается ошибкой.

Сценарий 46 основной регрессии очищает все опоры в пределах восьми блоков,
кроме трёх платформ. Дверь открывается параллельно второму прыжку: прежний
вариант позволял обход по боковому полу, а её открытая панель пересекала
нужный коридор. Теперь успех действительно проверяет оба прыжка и дверь.

Для масштаба используйте `/navtest load 1`, `/navtest load 10`,
`/navtest load 25` и `/navtest load 50` по очереди. Команда создаёт плоскую
арену, назначает каждому боту короткую цель, выводит число завершённых задач,
максимальное и среднее время тика, число поисков и посещённых узлов, затем
удаляет тестовых ботов.

Команда `/navtest loadgen <count>` повторяет тот же прогон с
`allowChunkGeneration=true`, чтобы проверить выдачу и освобождение navigation
tickets вместе с отдельным бюджетом генерации.

## Что проверяется

1. Добыча камня инструментом из обычного инвентаря и восстановление слотов.
2. Отмена добычи до первого тика без изменения блока и выбранного слота.
3. Отсутствие подходящего инструмента без изменения выбранного слота.
4. Отказ при попытке разрушить бедрок.
5. Подход, добыча и фактическое получение предмета.
6. Корректное завершение при полном инвентаре.
7. Отказ при отсутствии ресурсов.
8. Таймаут сбора отменяет дочернюю навигацию.
9. Явная отмена сбора.
10. Выбор лучшего меча, его реальная поломка и замена запасным мечом.
11. Стрельба стрелами из обычного инвентаря с расходом стрел и уроном цели.
12. Подъём на одноблочную ступень и последующая ближняя атака.
13. Отказ при недоступном ресурсе внутри оболочки из бедрока.
14. Повторный подход с другой стороны, если первая позиция изолирована.
15. Навигационное разрушение двухблочного препятствия с разрешённым инструментом.
16. Установка опоры из инвентаря для перехода через разрыв пола.
17. Открытие закрытой деревянной двери в узком коридоре.
18. Подход к лестнице по диагонали с земли и вертикальный подъём.
19. Перепланирование после появления блока на текущем маршруте.
20. Подъём по последовательности ступеней с проверкой опоры.
21. Проход по нижней плите с частичной collision shape.
22. Проход по узкому водному коридору при `allowWater=true`.
23. Открытие вручную открываемой медной двери в узком коридоре.
24. Прыжки через ямы шириной один, два и три блока.
25. Проход приседая через узкий туннель с нижними и верхними люками.
26. Дальний маршрут по frontier-сегментам вокруг длинной стены.
27. `BlockGoal` для твёрдого блока с завершением на соседней клетке.
28. Контролируемый спуск с уступа с ограничением `maxFallDistance`.
29. Открытие fence gate в узком коридоре.
30. Компенсация частичного моста после отмены навигации и после восстановления журнала из NBT.
31. Последовательное выполнение `MultiGoal`.
32. Последовательный `PatrolGoal`.
33. Мгновенный `LookAtGoal` с проверкой yaw.
34. Переход в Nether через `DimensionGoal`.
35. Удержание дистанции `EscortGoal`.
36. Проход по waterlogged нижней плите и проверка fluid/collision shape.
37. Прыжок через трёхблочный разрыв с дверями на блоках отрыва и приземления.
38. Проход через уже открытую дверь в узком коридоре.
39. Проход через открытый люк на уровне тела.
40. Проход под открытым люком на уровне головы.
41. Поворот рядом с открытым люком и его боковой створкой.
42. Длинный проход по глубокой воде под низкой крышей.
43. Маршрут по прямой на 32 блока с несколькими локальными снимками.
44. Прибытие к занятой другим ботом точке без столкновения.
45. Старт маршрута с края блока, когда центр игрока находится над пустой клеткой.
46. Подход к высокой цели через дорогу, вход на которую находится за пределами первого снимка.
47. Два прыжка через двухблочные разрывы с дверью на одиночной промежуточной платформе.
48. Возвращение бота из-под занятого игроком финиша через удалённый вход на приподнятую трассу.
49. Разрушение waterlogged-ступени с успехом, когда в клетке остаётся вода.
50. Повторный `goTo` из callback отмены: новая задача остаётся активной, внешний вызов получает `CANCELLED`.
51. Достижение цели в воздухе завершается после приземления.

Это ограниченная регрессия, а не проверка всех арен и сложных блоковых механизмов;
она включает живую проверку Efficiency-инструмента, waterlogged-геометрии,
составных целей и нагрузочных профилей.
